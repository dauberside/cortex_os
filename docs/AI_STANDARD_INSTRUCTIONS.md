# AI標準実装指示文

## 1. 目的

このドキュメントは、CORTEX OS プロジェクトにおいて AI に実装を依頼する際の標準前提を定義します。

これにより、以下を実現します:
- 一貫した実装品質の維持
- レビュー工数の削減
- プロジェクト固有のパターンとベストプラクティスの徹底

## 2. 必須ルール

### 基本方針
- **L1 実装時チェックリストを満たすこと**（`.github/pull_request_template.md` 参照）
- Next.js App Router / RHF+Zod / RBAC / tRPC / Prisma / TanStack Query パターンに沿って実装すること

### Next.js / React
- **RSC first**: デフォルトは Server Component として実装する
- **`use client` は必要最小限**: インタラクティブな操作が本当に必要な箇所のみに限定する
- **ファイルベース規約**: 新規ページ作成時は `loading.tsx` / `error.tsx` / `not-found.tsx` の要否を確認する
- **loading / error / empty state**: 必ず実装する

### データ取得 / 状態管理
- **初期表示**: RSC / fetch で扱うべきか確認する
- **動的操作**: TanStack Query / mutation で扱う
- **invalidate は最小粒度**: 必要な範囲のみを再検証する
- **server truth 優先**: サーバー側のデータを信頼し、クライアント側の状態と同期する

### API / tRPC / Prisma
- **input は Zod で定義**: すべての入力値をバリデーションする
- **認証と認可の責務を分離**: UI層とAPI層の両方でRBACを担保する
- **複数テーブル更新**: 整合性必須処理は `transaction` を使用する
- **response shape**: `select` / `include` で明示する
- **監査ログ対象の確認**: Create / Update / Delete 操作時は監査ログ必要性を確認する
- **not found の扱いを統一**: エラーハンドリングを一貫させる

### フォーム
- **RHF + Zod**: React Hook Form と Zod の組み合わせを検討し、必要な箇所で適用する
- **二重送信防止**: submit 中は disable する
- **送信前バリデーション**: クライアント側で事前チェックする
- **値変換は送信直前**: データ変換のタイミングを明確にする
- **標準 onSuccess フロー**: `toast → close / reset → invalidate / redirect` の流れを整理する
- **エラー表示の責務**: field / form / toast のどれで表示するか明確にする

### 削除 / 監査
- **confirm が必要な操作か確認**: 削除などの破壊的操作には確認ダイアログを実装する
- **soft delete vs 物理削除**: どちらを使うか明確にする
- **復元要件の有無**: ビジネス要件を確認する
- **toast 文言**: 既存ルールに沿った一貫性のある表現にする
- **onDelete / 関連削除の整合性**: 外部キー制約と CASCADE の動作を確認する

### UI / 権限
- **filter / sort / pagination / search params**: 一覧画面では必要性を確認する
- **empty state / loading state**: ユーザー体験を考慮して実装する
- **RBAC**: UI層とAPI層の**両方**で担保する
- **redirect 後の導線**: ユーザーが迷わない自然なフローにする

## 3. 出力形式

AI が実装を行う際は、以下の形式で進めてください:

### 実装前
1. **方針を簡潔に示す**: どのような変更を行うか、なぜその方法を選択したかを説明する
2. **変更ファイルを明示する**: どのファイルを作成/変更するかリストアップする
3. **L1 の該当項目を確認**: どのチェックリスト項目が関連するかを事前に把握する

### 実装中
4. **段階的に進める**: 大きな変更は小さなステップに分割する
5. **説明を添える**: 各変更の意図をコメントまたは説明として記述する

### 実装後
6. **L1 自己確認**: 実装完了後、関連するチェックリスト項目を満たしているか自己評価する
7. **テスト観点を提示**: 動作確認すべきポイントを明示する
8. **影響範囲を明記**: UI / API / DB スキーマ / 権限 / 既存機能への影響を整理する
