## 1. システム概要

福祉・介護分野における重度障害者支援の業務日誌・記録システム。日々の支援記録、バイタルサイン、ヒヤリハット、申し送り事項などを一元管理し、利用者のQOL向上と支援の質の向上を目指す。

### 1.1 システムの主軸（Plan → Do → Fact → Safety）

| レイヤ                 | 内容                     | 対応機能                  |
| ---------------------- | ------------------------ | ------------------------- |
| **L1: Plan（計画）**   | 個別支援計画             | 利用者管理・印刷帳票      |
| **L2: Do（実施）**     | 日々の支援記録・業務日誌 | ガイド記録・業務日誌      |
| **L3: Fact（実績）**   | サービス提供実績         | ServiceRecord（自動生成） |
| **L4: Safety（安全）** | 事故・ヒヤリハット       | インシデント管理          |

## 5. データベース構成

### 5.1 主要テーブル

```
User (職員)
├── role: STAFF / LEAD / MANAGER
└── (1:N) → CareRecipient (利用者)
            ├── (1:1) → Assessment（段階的廃止予定）
            ├── (1:N) → GuideRecord（ガイド記録）
            │           └── (1:1) → ServiceRecord（自動生成）
            ├── (1:N) → DailyLogEntry（業務日誌明細）
            └── deletedAt（論理削除）

Unit (ユニット)
├── (1:N) → UnitStaff（職員紐付け）
├── (1:N) → UnitRecipient（利用者紐付け）
└── (1:N) → DailyLog（業務日誌ヘッダー）
            └── (1:N) → DailyLogEntry

AuditLog (監査ログ)
└── action: View/Edit/Delete/Approve/BackToDraft
```

### 5.2 重要な注意事項

- **論理削除**: `deletedAt`で論理削除。物理削除は原則禁止。
- **5年保存**: サービス提供記録は提供した日から5年間保存。
- **Assessment段階廃止**: CareRecipientにSSoT統合済み。

はい。制度と実務を分けて整理すると、こう考えるのが安全です。

結論
システム設計は 案Bを基本 にして、手帳情報は別管理 にするのが実務上いちばん無難です。
理由は、障害福祉サービスの対象や支援ニーズは 手帳の有無と1対1では対応しない からです。厚労省も、手帳を所持していない精神・発達障害者等にも、障害特性に応じた支援が必要だと明示しています。令和4年の全国調査でも、手帳非所持だが障害福祉サービス等を利用している者が推計22.9万人 います。  ￼

質問1: 重複障害の定義と実態

1) どの程度の割合で存在するか
「身体・知的・精神のうち複数を併せ持つ利用者が全国で何％か」という、そのまま使える単一の公式統計は見当たりませんでした。
ただし、厚労省の「令和4年生活のしづらさなどに関する調査」では、障害者手帳所持者総数は 610.0万人、内訳は 身体415.9万人、療育114.0万人、精神120.3万人 で、しかも「手帳の種類」は複数回答です。つまり、少なくとも一定数は複数手帳・重複障害に該当しており、重複は例外的ではないと見てよいです。厳密な重複人数はこの表だけでは確定できません。  ￼

2) 複数の障害者手帳を同時に所持できるか
可能です。
各手帳は別制度です。厚労省は、身体障害者手帳・療育手帳・精神障害者保健福祉手帳をそれぞれ独立した制度として案内しています。さらに自治体の案内でも、愛の手帳（療育手帳）と精神障害者保健福祉手帳の両方を取る方がいることが明記されています。埼玉県系の案内でも、3種類の手帳を並列の制度として扱っています。  ￼

質問2: システム設計における障害種別の扱い

案A: 手帳所持状況から障害種別を自動判定
これは 補助的には使えても、主データにするのは危険 です。
理由は3つあります。
	1.	手帳未所持でもサービス利用者がいる
　先ほどの通り、手帳非所持でサービス利用している人がいます。手帳起点で自動判定すると取りこぼします。  ￼
	2.	療育手帳は全国一律の法律制度ではなく、自治体運用
　厚労省も、療育手帳は各自治体が判定基準等の運用方法を定めて実施していると案内しています。つまり、療育手帳の有無だけで全国一律のデータ定義にするのはやや不安定です。  ￼
	3.	“障害種別”と“制度上の証票”は別物
　手帳は福祉サービスや各種支援のための証票であって、現場で必要なのはしばしば「主たる障害」「支援上重要な特性」「医療的ケア」「行動面の支援必要性」などです。手帳だけでは支援設計に足りません。障害支援区分の認定も、手帳の種類そのものではなく、認定調査・医師意見書・審査会で支援必要度を判定します。  ￼

案B: 障害種別を手帳とは独立して手動入力
こちらを 推奨 します。
ただし、手動入力だけにせず、次のように分けると実務で強いです。
	•	手帳情報
身体障害者手帳 / 療育手帳 / 精神障害者保健福祉手帳
等級、交付自治体、交付日、有効期限、再判定予定、備考
	•	障害特性・障害種別
身体 / 知的 / 精神 を複数選択可
さらに必要なら、発達障害、難病、高次脳機能障害、医療的ケア、強度行動障害などを別項目で管理
	•	支援判定情報
障害支援区分、認定日、有効期間、医師意見書関連、特記事項

この分離なら、制度変更や自治体差にも強く、帳票や自治体提出資料にも合わせやすいです。  ￼

質問3: 障害支援区分との関係

重複障害だからといって、障害支援区分認定に“一律の特別加算”が付く仕組みは確認できませんでした。
障害支援区分は、認定調査、医師意見書、一次判定、二次判定（市町村審査会） で、支援の必要度を判定します。つまり、重複障害は「その結果として支援必要度が高く出る」ことはあり得ますが、“重複だから自動で区分加算”ではありません。  ￼

一方で、報酬算定や受入体制の評価 には、重度障害者支援加算などの加算体系があります。これは区分認定そのものとは別です。令和6年度報酬改定でも、重度障害者支援加算の評価拡充が行われています。  ￼

質問4: 実務上の推奨

最適解は「手帳」と「障害種別」を分けて持つことです。
現場向けには、次の設計が扱いやすいです。

推奨モデル
	•	handbooks
	•	handbook_type: physical / intellectual / mental
	•	grade
	•	issuing_authority
	•	issue_date
	•	expiry_date
	•	reexamination_due
	•	status
	•	disability_profile
	•	physical_disability: boolean
	•	intellectual_disability: boolean
	•	mental_disability: boolean
	•	developmental_disability: boolean
	•	intractable_disease: boolean
	•	higher_brain_dysfunction: boolean
	•	notes
	•	support_needs
	•	support_level (障害支援区分)
	•	behavioral_support_flag
	•	medical_care_flag
	•	communication_support_flag
	•	mobility_support_flag

運用ルール
	•	手帳情報の更新は事務担当が管理
	•	障害種別・支援特性は相談支援専門員やサービス管理責任者が確認
	•	「主たる障害」は1つ選べても、複数該当を保持する
	•	帳票や集計では
「手帳ベース集計」
「障害特性ベース集計」
を分けて出せるようにする


## フォーム最新状況（制度情報セクション）

### 現在の方針
- 制度情報セクション内の「障害者手帳」は、**手帳情報と障害種別を分離して管理する方針**。
- 障害種別の判定を手帳所持有無から自動確定するのではなく、**手帳はあくまで証票情報として保持**する。
- UI上は「身体障害者手帳」「愛の手帳（療育手帳）」「精神障害者保健福祉手帳」の3区分を表示。
- 利用者が複数手帳を所持しているケースを想定し、**複数選択可能**とする。

### 手帳ごとの入力仕様
#### 1. 身体障害者手帳
- 選択方式: チェックボックス + 等級プルダウン
- 保存対象: 所持有無、等級
- 等級選択肢:
  - 未設定
  - 1級
  - 2級
  - 3級
  - 4級
  - 5級
  - 6級
- 備考: 7級は単独交付対象ではないため、通常の選択肢には含めない。

#### 2. 愛の手帳（療育手帳）
- 選択方式: チェックボックス + 程度区分プルダウン
- 保存対象: 所持有無、程度区分
- **基準は東京都の愛の手帳基準で統一**する。
- 程度区分選択肢:
  - 未設定
  - 1度（最重度）
  - 2度（重度）
  - 3度（中度）
  - 4度（軽度）
- 備考: 以前の `B2（軽度）` 表記は廃止し、愛の手帳基準に合わせて `1度〜4度` に統一する。

#### 3. 精神障害者保健福祉手帳
- 選択方式: チェックボックス + 等級プルダウン
- 保存対象: 所持有無、等級
- 等級選択肢:
  - 未設定
  - 1級
  - 2級
  - 3級

### 画面実装上の補足
- 手帳未選択時は等級・程度区分を未設定のまま保持可能。
- 各手帳は独立して入力できるため、重複障害・複数手帳所持にも対応可能。
- フォーム上の手帳情報は制度上の証票管理であり、**障害種別の最終判定項目としては使わない**。
- 今後、障害種別・支援特性・障害支援区分は別セクションまたは別データ構造で管理する前提。


### 引き継ぎメモ
- 現在のUIラベルは「制度情報（手帳・年金/手当・精神科/発達・介護保険）」配下に配置。
- 障害者手帳ブロックでは、各手帳カードにチェックボックスと等級プルダウンを配置している。
- 療育手帳については全国共通基準ではなく東京都運用の**愛の手帳基準を採用**するため、今後も文言・選択肢を東京都基準で揃える。
- 将来全国対応を行う場合は、内部データ構造で療育手帳と愛の手帳表示名を分離できるようにする余地あり。

### 引き継ぎ用：現状確認で修正すべき内容
- 利用者詳細画面（`src/app/recipients/[id]/page.tsx`）では、知的障害系手帳の表示ラベルがセクションごとに不統一。
  - 基本情報セクション: `愛の手帳（療育手帳）`
  - 障害福祉制度情報セクション: `療育手帳`
- 今回の運用方針は**東京都の愛の手帳基準で統一**としているため、表示ラベルは全画面で `愛の手帳（療育手帳）` に揃える必要がある。
- 現在の詳細画面では、知的障害系手帳の程度区分は `intellectualHandicapGrade` をそのまま表示している。
  - そのため、保存値が `1度 / 2度 / 3度 / 4度` であれば愛の手帳基準として表示可能。
  - 一方で、保存値が `A1 / A2 / B1 / B2` のままだと、そのまま旧表記で表示されてしまう。
- したがって、**フォーム選択肢の統一だけでは不十分**で、既存データおよび表示ロジックの整合確認が必要。

## Prisma + Neon 接続エラー解決済み (2026-03-09)

### ✅ 解決済み

`pnpm db:push` の `P1001` エラーは解決しました。

### 根本原因

**Neon の direct endpoint への接続タイムアウト**

- Neon のコンピュートは非アクティブ時にスケールゼロになる
- Prisma の標準タイムアウトでは、コンピュートの起動を待てずにタイムアウト
- `connect_timeout` と `pool_timeout` を追加することで解決

### 最終的な修正内容

#### 1. `prisma.config.ts`

```typescript
datasource: {
  url:
    process.env["DIRECT_URL"] ??
    process.env["CORTEX_DATABASE_DATABASE_URL_UNPOOLED"] ??
    process.env["DATABASE_URL"],
},
```

**重要**: Prisma の `db push` / `migrate` には **direct URL が必須**。pooler では動作しません。

#### 2. `.env` の `DIRECT_URL` パラメータ

```
DIRECT_URL=postgresql://user:pass@ep-xxx.c-4.us-east-1.aws.neon.tech/neondb?uselibpqcompat=true&sslmode=require&connect_timeout=30&pool_timeout=30
```

**追加したパラメータ:**
- `uselibpqcompat=true` - pg ドライバの SSL モード警告対応
- `connect_timeout=30` - 接続タイムアウトを 30秒に延長
- `pool_timeout=30` - プールタイムアウトを 30秒に延長

**削除したパラメータ:**
- `sslaccept=accept_invalid_certs` - 不要なパラメータ（Prisma/pg が認識しない）
- `pgbouncer=true` - direct URL には不要

#### 3. `.env` の `DATABASE_URL` パラメータ

```
DATABASE_URL=postgresql://user:pass@ep-xxx-pooler.c-4.us-east-1.aws.neon.tech/neondb?sslmode=require
```

**用途**: アプリケーションの通常クエリ用（Neon Serverless Adapter で使用）

### 検証結果

| 接続方法 | DATABASE_URL (pooler) | DIRECT_URL (direct) |
|---------|---------------------|---------------------|
| Neon Serverless Driver | ✅ 成功 | ✅ 成功 |
| pg Driver | ✅ 成功 | ❌ → ✅ (タイムアウト追加後) |
| Prisma CLI (`db push`) | ❌ 非対応 | ❌ → ✅ (タイムアウト追加後) |

### Prisma 7.x + Neon の重要な知見

#### 1. Prisma CLIはpoolerを使えない

[Prisma公式](https://github.com/prisma/prisma/discussions/23589) および [Neon公式ドキュメント](https://neon.com/docs/guides/prisma) によると:

- **`prisma migrate`** と **`prisma db push`** は direct connection が必須
- PgBouncer（Neon pooler）では DDL 操作が非対応
- `DATABASE_URL` (pooler) はアプリケーション用、`DIRECT_URL` (direct) はCLI用

#### 2. Prisma 7.xの設定方針

- `schema.prisma` に `url` / `directUrl` を書くと **エラーになる**
- すべて `prisma.config.ts` で管理する必要がある

#### 3. Neonのコンピュート起動

- スケールゼロからの起動に数秒かかる
- デフォルトタイムアウトでは間に合わない場合がある
- `connect_timeout=30&pool_timeout=30` で解決

### アプリケーション側の構成

`src/lib/prisma.ts` では正しく Neon Serverless Adapter を使用:

```typescript
const adapter = new PrismaNeon({ connectionString: process.env.DATABASE_URL });
return new PrismaClient({ adapter });
```

これにより、アプリケーションは pooler 経由で高速接続できる。
